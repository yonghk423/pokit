# 이미지 로딩과 캐시 정책

갱신일: 2026-11-10

스토어 상품이 탭 이동마다 늦게 나타나고, 달력의 판·집게·날짜가 따로 표시되는 문제를 줄이기 위한 구현 기준입니다. 다이어리 사진은 작은 미리보기에서 원본을 먼저 읽는 작업을 줄입니다. 이 문서의 용량은 이미지 캐시 기준이며 사용자 사진·다이어리·다운로드한 달력의 총 저장 용량 제한이 아닙니다.

## 현재 적용한 방식

### 내장 스토어 상품

[storeArtwork.ts](../../src/pages/day-plan/lib/storeArtwork.ts)는 판, 표지, 파란 집게, 검은 집게, 메쉬 휴지통, 클래식 카메라 6개를 `Image.loadAsync`로 읽습니다. 각 이미지의 가로·세로를 최대 768px로 제한해 디코딩하고, 준비된 `ImageRef`와 진행 중 Promise를 모듈에서 공유합니다.

- 6개 모두 준비되면 스토어 콘텐츠를 표시합니다. 준비 중에는 스켈레톤, 실패하면 재시도 버튼을 표시합니다.
- 탭을 다시 열 때 이미 준비된 객체를 재사용합니다. 화면이 다시 생성되어도 같은 세션의 준비 작업을 반복하지 않습니다.
- 클립보드는 같은 이미지에서 세 영역을 잘라 표시하는 구조를 유지하지만, 세 영역이 같은 준비된 이미지 객체를 사용합니다.
- 대표 표지의 날짜도 배경 준비 후 함께 표시합니다.
- 준비는 `useStoreArtwork`를 사용하는 첫 화면이 마운트될 때 시작합니다. 앱 시작 시 미리 준비하도록 연결한 상태는 아닙니다.
- 준비된 객체는 앱 실행 세션 동안 유지됩니다. 앱 재시작 후에도 RAM 데이터가 남는 것은 아닙니다.

관련 화면: [스토어](../../app/(tabs)/calendar.tsx), [클립보드 달력](../../src/pages/day-plan/ui/HeroClipboardCalendar.tsx), [대표 표지](../../src/pages/day-plan/ui/CityCalendarPackCover.tsx), [집게](../../src/pages/day-plan/ui/HeroBlueClipPreview.tsx).

### 다운로드한 달력 상품

달력 원본 50개는 위 6개 객체에 포함하지 않습니다. 목록 미리보기는 로컬 다운로드 파일을 Expo Image로 표시하며 `cachePolicy="memory"`를 사용합니다. 각 미리보기는 `onDisplay` 전까지 스켈레톤으로 가립니다. 50개 전체가 모두 준비될 때까지 목록을 막는 방식은 아닙니다.

다운로드 파일은 사용자가 설치한 콘텐츠입니다. 캐시 정리로 삭제하지 않습니다. 사용자가 팩을 삭제할 때 다운로드 폴더를 제거하며, 내장 대표 표지는 삭제 대상에 포함하지 않습니다. 종이와 나뭇잎 장식은 다운로드 및 완료 검사에서 제거된 상태입니다.

### 다이어리 사진 썸네일

[heroOriginalPhoto.ts](../../src/pages/day-plan/lib/heroOriginalPhoto.ts)는 원본을 저장한 뒤 [photoPreview.ts](../../src/pages/day-plan/lib/heroPhotoPreview.ts)의 미리보기 생성을 기다립니다. 저장 시 작업이 추가되는 대신 목록에서 처음 생성하는 부담을 앞당깁니다. 생성 실패 시 원본을 사용할 수 있도록 폴백합니다.

[HeroSceneImage.tsx](../../src/pages/day-plan/ui/HeroSceneImage.tsx)는 레이아웃 크기를 확인한 뒤, 긴 변이 400pt 이하이고 `hero-photos/photo-…` 경로인 사진에 미리보기를 사용합니다. 미리보기 확인·생성 중에는 원본부터 로딩하지 않고 스켈레톤을 유지합니다.

미리보기는 긴 변 최대 512px의 WebP이며, `Caches/hero-previews-v1/`에 저장합니다. 기존 파일은 재사용하고 신규 생성은 직렬 처리합니다. 모든 일러스트·편집 결과·사진 경로에 이 규칙이 적용되는 것은 아닙니다.

## 용량 제한과 저장 위치

| 대상 | 현재 기준 | 제한의 의미 |
|---|---|---|
| Expo 이미지 디스크 캐시 | 50 MiB | iOS 네이티브 캐시의 정리 목표 |
| Expo 이미지 메모리 캐시 | 32 MiB, 최대 80개 | iOS 네이티브 캐시 설정 |
| 사진 미리보기 파일 | 32 MiB | 새 파일 생성 후 오래된 파일부터 정리 |
| 내장 상품의 공유 ImageRef | 6개, 각 최대 768×768px | RGBA 픽셀 기준 최대 약 14 MiB, 별도 유지 객체 |
| 사용자 원본·다운로드 달력 | 위 캐시 제한에 포함하지 않음 | 사용자 데이터·설치 콘텐츠 |

[imageCachePolicy.ts](../../src/application/imageCachePolicy.ts)의 네이티브 제한은 현재 iOS에만 적용됩니다. 이전 개발 클라이언트가 API를 제공하지 않으면 설정 실패를 개발 로그에 남깁니다. 네이티브 정리는 즉시 적용되는 절대 상한이 아니며, 공유 ImageRef와 화면 렌더링 버퍼까지 포함한 앱 전체 RAM 상한도 아닙니다. 디스크 캐시 50 MiB와 미리보기 32 MiB 역시 앱 전체 저장 공간을 82 MiB로 제한한다는 뜻이 아닙니다.

## Expo 기능을 선택한 이유

| 기능 | 현재 용도 |
|---|---|
| `cachePolicy` | 이미지 종류에 맞춰 메모리·디스크 재사용 정책 지정 |
| `Image.loadAsync` | 내장 상품을 미리 디코딩하고 준비된 객체 공유 |
| `prefetch` | 이번 내장 상품 준비 경로에서는 사용하지 않음 |
| `useImage` | 이번 내장 상품 준비 경로에서는 사용하지 않음 |

`prefetch`는 캐시 준비, `useImage`는 컴포넌트에서 이미지 준비 상태를 다루는 데 사용할 수 있습니다. 현재는 여러 화면이 공유하는 `loadAsync` 결과로 준비와 재사용을 처리하므로 같은 작업을 추가하지 않았습니다. 기능을 모두 사용하는 것이 성능 목표는 아닙니다. 화면 진입 전에 준비가 끝나 있는지와 실제 표시 비용을 확인해야 합니다.

## 투명 상품 이미지

집게와 메쉬 휴지통은 알파 채널을 보존한 PNG를 사용합니다. `loadAsync`가 만든 ImageRef에는 화면 컴포넌트의 `useAppleWebpCodec` 설정이 적용되지 않으므로, 투명 WebP를 이 경로로 준비할 때 나타나는 검은 직사각형 문제를 피하기 위한 조치입니다. 원본 WebP의 알파 값과 변환 PNG의 알파 값이 같은지 확인했습니다. 집게 미리보기의 추가 그림자 레이어도 제거했습니다. 실기기 표시 결과는 별도 확인이 필요합니다.

집게 미리보기는 PNG 전환 후에도 직사각형으로 잘린다는 실기기 보고가 있어, ImageRef의 실제 가로·세로 비율로 컨테이너를 계산하도록 추가 수정했습니다. 컨테이너와 이미지 비율을 일치시킨 후 `contentFit="fill"`, `allowDownscaling={false}`로 표시합니다. 이 작은 상품은 이미 미리 디코딩되어 있으므로 화면에서 다시 축소 처리할 필요가 없습니다. 비율 수정 후 실기기 결과 확인은 아직 필요합니다. 따라서 검은 직사각형의 원인을 WebP 투명도 문제 하나로 확정하지 않습니다.

## 수정할 때 지킬 규칙

1. 내장 대표 썸네일을 다운로드 파일과 연결하거나 팩 삭제 대상으로 넣지 않습니다.
2. 준비된 상품 이미지를 다시 URI로 바꿔 각 부품에서 따로 읽지 않습니다.
3. 이미지가 준비됐다는 과거 기록만으로 실제 이미지가 지금 메모리에 있다고 가정하지 않습니다.
4. 탭 이동마다 전역 캐시를 비우지 않습니다. 현재 팩 삭제 시 전역 Expo 캐시를 지우는 코드가 있으므로, 삭제 직후 다른 사진은 다시 로딩될 수 있습니다.
5. 50개 원본 전체를 공유 ImageRef에 추가하지 않습니다. 상품 추가 시 메모리 예산과 준비 실패의 영향을 함께 검토합니다.
6. 축소 디코딩 크기를 바꿀 때 실기기의 선명도를 확인합니다. 특히 전체 화면 달력은 768px 결과의 품질 확인이 필요합니다.
7. 캐시 크기나 준비 방식 변경 시 이 문서와 관련 검사도 함께 갱신합니다.

## 검증 상태와 다음 확인

적용 당시 TypeScript 검사와 이미지 캐시 정책·원본 사진 관련 테스트 7개가 통과했습니다. 실기기 성능 측정과 실제 표시 순서 확인은 아직 완료하지 않았습니다. 로딩이 전혀 없다고 보장하지 않습니다.

실기기에서 다음을 확인합니다.

- 첫 스토어 진입과 두 번째 진입을 구분해 이미지 표시 시간을 측정합니다.
- 상단 탭 왕복 시 판·집게·날짜가 따로 나타나는지 확인합니다.
- 신규 사진 저장 후 목록 진입, 기존 사진 다수의 목록 진입을 각각 확인합니다.
- 네트워크 끊김·이미지 준비 실패 시 스켈레톤에 갇히지 않고 재시도가 가능한지 확인합니다.
- 개발 서버 연결 빌드와 Release 빌드를 구분합니다. 개발 중 번들 에셋은 Metro에서 제공될 수 있으므로 네트워크 영향을 분리합니다.
- 앱 재시작, 메모리 압박, 팩 삭제·재다운로드 후 동작과 캐시 용량을 확인합니다.

첫 진입이 느리다면 앱 초기 화면이 안정된 이후 준비를 시작하는 개선을 검토합니다. 이는 현재 구현 완료 항목이 아닙니다.
