# 다이어리 사진 썸네일 최적화

갱신일: 2026-11-10

## 목적

사진이 작은 카드 여러 장으로 보이는 화면에서 원본 파일을 반복해서 읽고 디코딩하는 비용을 줄입니다. 작은 표시에는 별도의 경량 미리보기를 사용하고, 사진 원본은 보존해 큰 화면·편집·내보내기에서 사용합니다.

## 현재 동작

1. 사진을 가져오면 [heroOriginalPhoto.ts](../../src/pages/day-plan/lib/heroOriginalPhoto.ts)가 사진 선택기의 임시 URI를 앱 문서 폴더의 `hero-photos/`에 복사합니다. 이후 단계는 이 보존된 원본 URI를 기준으로 진행합니다.
2. 원본 저장 직후 [heroPhotoPreview.ts](../../src/pages/day-plan/lib/heroPhotoPreview.ts)의 미리보기를 생성합니다. 생성은 사진 저장 흐름에서 기다리므로 미리보기가 준비되기 전에 저장 작업이 완료되지 않습니다.
3. 미리보기는 긴 변을 최대 **512px**로 축소하고 **WebP, 품질 0.88**로 인코딩합니다. 원본의 크기가 512px 이하라면 크기는 그대로 두고 WebP로 인코딩합니다.
4. 미리보기 파일은 앱 샌드박스의 `Caches/hero-previews-v1/`에 저장합니다. 이는 앱 설치 번들이 아니며, 앱을 사용하는 기기의 로컬 저장공간을 사용합니다. 운영체제가 캐시 파일을 제거할 수 있으므로 원본에서 다시 만들 수 있습니다.
5. [HeroSceneImage.tsx](../../src/pages/day-plan/ui/HeroSceneImage.tsx)는 실제 이미지 뷰의 긴 변이 **400pt 이하**이고 파일이 `hero-photos/photo-…` 원본일 때 미리보기를 선택합니다. 뷰 크기 측정과 미리보기 조회·생성이 끝나기 전까지는 원본을 먼저 그리지 않고 스켈레톤을 유지합니다. 조건에 해당하지 않는 큰 뷰는 원본을 사용합니다.
6. 화면에 그릴 때 Expo Image의 `allowDownscaling`과 `enforceEarlyResizing`을 켜고, 로컬 사진은 메모리 캐시를 사용합니다. 이 디코딩·메모리 캐시 정책은 별도 미리보기 파일 저장 정책과 다릅니다.

## 중복 생성과 오류 처리

- 같은 원본 URI의 생성 요청이 동시에 들어오면 진행 중 Promise를 공유합니다.
- 여러 사진을 한꺼번에 디코딩하지 않도록 새 미리보기 생성은 한 번에 하나씩 순차 처리합니다.
- 이미 같은 이름의 미리보기가 있으면 재사용합니다.
- 변환이나 파일 작업에 실패하면 원본 URI를 반환합니다. 사진 표시가 실패하는 대신 원본을 사용할 수 있지만, 이 경우 작은 뷰의 로딩 비용 절감은 적용되지 않습니다.
- 변환 중 만들어진 임시 WebP 파일은 이동 후 정리합니다.

## 저장공간 정책

미리보기 디렉터리의 정리 목표는 **32 MiB**입니다. 새 미리보기를 저장한 뒤 파일 수정 시각이 오래된 순서로 지워 공간을 회수합니다. 현재 요청으로 만든 파일은 정리 대상에서 제외합니다. 따라서 이는 앱 전체 저장공간의 절대 상한이 아니며, 단일 파일이 매우 크거나 정리 중이면 잠시 32 MiB를 넘을 수 있습니다.

| 파일 | 위치 | 사용처 | 삭제·복구 |
|---|---|---|---|
| 사진 원본 | 앱 Documents의 `hero-photos/` | 큰 사진 뷰, 편집·내보내기, 다이어리 데이터 | 사용자 데이터로 보존. 미리보기 정리 대상 아님 |
| 경량 미리보기 | 앱 Caches의 `hero-previews-v1/` | 400pt 이하 작은 사진 뷰 | 오래된 파일부터 정리 가능. 필요하면 원본에서 재생성 |

사진 삭제 시 [heroArtworkCleanup.ts](../../src/pages/day-plan/lib/heroArtworkCleanup.ts)는 삭제 표시된 원본을 다이어리에서 참조하지 않는 경우 Documents에서 정리합니다. 현재 이 코드는 `Caches/hero-previews-v1/`의 해당 미리보기를 즉시 지우지 않습니다. 고아 미리보기는 오래된 파일 정리나 운영체제의 캐시 회수 때까지 남을 수 있지만, 32 MiB 정리 목표의 대상입니다. 원본 보존 정책이나 백업 포함 범위를 바꿀 때는 해당 구현도 함께 확인해야 합니다.

## 적용 범위와 제한

- 원본 경로가 `hero-photos/photo-…`인 업로드 사진만 자동 미리보기 대상으로 삼습니다.
- 미리보기는 원본 대체본이 아닙니다. 편집·내보내기 결과에는 썸네일 URI를 전달하지 않습니다.
- 일러스트 에셋, 원격 이미지, 생성 이미지 등 모든 이미지에 일괄 적용되는 기능은 아닙니다.
- 400pt 기준은 실제 렌더링 뷰 크기 기준입니다. 화면 확대나 레이아웃 변경에 따라 원본 사용 여부가 달라질 수 있습니다.
- 첫 사진 저장 때 원본 복사 외에 WebP 변환이 추가되므로 사진 저장 완료가 늦어질 수 있습니다. 그 비용을 작은 사진 목록에서의 반복 디코딩 감소와 맞바꾼 구조입니다.
- 썸네일의 512px은 픽셀 크기이지 파일 용량 보장은 아닙니다. 실제 바이트 크기는 원본 내용과 압축 결과에 따라 달라집니다.

## 변경 시 지킬 기준

1. 작은 사진 목록에서는 썸네일을 사용하고 큰 보기·편집·내보내기는 원본을 사용합니다.
2. 원본을 미리보기 저장 위치로 옮기거나, 미리보기를 원본 대신 저장하지 않습니다.
3. 용량 정리는 재생성 가능한 미리보기만 대상으로 하고 Documents의 원본은 건드리지 않습니다. 사진 삭제 때 고아 미리보기도 바로 지우도록 바꾸면 원본 참조 보호와 함께 검증합니다.
4. 썸네일 크기나 품질을 바꾸면 작은 카드와 큰 화면에서 모두 선명도·표시 시간을 확인합니다.
5. 캐시 경로·정리 기준·적용 조건을 변경하면 이 문서와 [이미지 로딩과 캐시 정책](image-loading-and-cache.md)을 함께 갱신합니다.

## 확인 항목

- 신규 업로드 직후 사진 저장이 끝나고 작은 목록에 썸네일이 표시되는지
- 여러 장이 있는 목록을 처음 열 때 스켈레톤에서 썸네일로 자연스럽게 바뀌는지
- 큰 카드·편집기·내보내기에서 원본 해상도가 사용되는지
- 썸네일 생성 실패와 캐시 파일 삭제 후에도 원본으로 표시되거나 미리보기가 재생성되는지
- 반복 탭 이동에서 재생성·원본 재디코딩이 불필요하게 반복되지 않는지
- 저장공간 정리 후 Documents 원본과 다이어리 참조가 유지되는지
